# Taste Profile
- Prefers Effect-TS's `Option` type over nullable/undefined types (`string | undefined`). Confidence: 0.9
- Prefers providing sensible default values (e.g., `DEFAULT_AGENTS_MD = ""`) to eliminate nullable types entirely instead of allowing `undefined`. Confidence: 0.8
- Prefers validating changes by running CI (`npm run ci` / `bun run ci`) before considering implementation complete — lint, typecheck, and tests must all pass. Their approved implementation plans include "run `bun run ci` to verify" as the final gate. Confidence: 0.8
- Prefers testing functionality through the full application pipeline (end-to-end / integration style) rather than testing individual internal functions in isolation — rejects direct calls to internal helpers in tests. Confidence: 0.9
- Prefers parameterizing functions with explicit values (e.g., `discoverSkills(home: string)`) rather than reading from `Config`/environment internally, to prevent service dependency leakage through call chains and keep modules easier to test. Confidence: 0.7
- Dislikes branded type patterns that can be trivially bypassed — rejects both `as` casts and Schema's `.make()` constructor. When branding is used, the only valid ways to obtain a branded value should be through the real generation pipeline or Schema parsing/decoding at boundaries, so circumvention requires deliberate subversion. Confidence: 0.9
- Prefers Effect's `Schema.brand` as the mechanism for branded types when working in Effect-TS codebases — values flow through Schema at module boundaries, making `as`-style casts unnatural. Confidence: 0.7
- Uses a plan-driven workflow for non-trivial implementation tasks: approved plans live as markdown under `~/.commandcode/plans/` and work is kicked off with "Implement <plan path>" — expects the agent to follow the plan's steps (tracked via todos) rather than re-designing the approach. Confidence: 0.8
- Effect-TS error design pattern: domain errors are defined as `Schema.TaggedErrorClass` classes surfaced through a union alias (e.g., `SessionError = SessionNotFound | SessionStorageError`); low-level `PlatformError`s get classified into domain errors at the service layer (e.g., reason `NotFound` → `SessionNotFound`), with error mapping via `Effect.fnUntraced(body, transform)` / `Effect.mapError`. Confidence: 0.7
- At application boundaries, recovers from typed errors with `Effect.catchTag` plus a graceful fallback (e.g., stale session id → log a warning and start a fresh session) instead of `Effect.orDie`/crashing. Confidence: 0.7
- Projects run on Effect v4 ("effect-smol") — v3-era APIs like `Effect.zipRight` do not exist; reach for v4 equivalents (`Effect.andThen`, `Effect.fnUntraced`). Confidence: 0.6
- When encountering `unknown` types or `as` type assertions, prefers fixing the data model at the source (tightening return types, adding proper interfaces/schemas at the producing function) rather than casting at each consumption site — a "fix the root cause" approach to type safety. Confidence: 0.85
- At I/O boundaries (HTTP request parsing, JSON deserialization, file reads), prefers parsing with Schema (`Schema.decodeUnknownSync` or `Schema.decodeUnknown`) with `{ onExcessProperty: "ignore" }` for partial/lenient schemas rather than using `as` type assertions — even in test helpers. Confidence: 0.7
- Follows Effect best practice of composing all layers at the application entry point and providing them at once ("one layer, one provide"), rather than scattering `Effect.provide` calls throughout the codebase (tests, library code, subroutines). Confidence: 0.8
- Prefers enabling strict Effect diagnostics (like `strictEffectProvide`) as errors in tsconfig to enforce architectural discipline — treats these diagnostics as guards against layer composition mistakes, not nuisances. Confidence: 0.8
- Prefers deep structural refactors over per-line diagnostic suppressions to resolve compiler errors — treats diagnostics as signals of architectural issues to fix at the root rather than surface-level annoyances to silence. Confidence: 0.9
